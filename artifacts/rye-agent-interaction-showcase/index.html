The operating vision

Review is a bootstrap phase—not a permanent tax.

Humans approve the autonomy policy. Agents act inside it. Review teaches the system which patterns are safe to automate and remains the path for genuine exceptions.

01 / OBSERVE

Capture automatically.

Preserve relevant evidence and activity with provenance. Observation should not require a person to click “approve.”

02 / ACT

Execute within policy.

When authority, claim type, scope, evidence, and risk match an accepted rule, the agent completes the write.

03 / ESCALATE

Ask on exception.

Novel, sensitive, contradictory, low-confidence, or out-of-scope interpretations become candidates or disputes.

04 / ADAPT

Turn repetition into policy.

Repeated review outcomes propose a narrow autonomy rule. An administrator approves the rule once—not every matching case.

Four modes of agent autonomy

The system chooses the lightest safe path for each interaction.

Mode 0
ObserveAutomatic evidence, events, artifacts, and audit.
Mode 1
DirectThe user’s explicit instruction is the approval. Do not ask twice.
Mode 2
Policy-drivenAuto-promote a familiar pattern inside a pre-approved envelope.
Mode 3
ExceptionEscalate ambiguity, conflict, sensitivity, or policy drift.

A narrow rule, not broad trust

Example autonomy policy for account operations.

WHEN domain = account-updates
AND claim = account_review_date
AND authority = account_owner
AND speech_act = confirmed
AND evidence_ref = present
THEN promote + audit
✓ All conditions match
Agent acts
! Anything differs

Agent guardrails

↗

Domain-scoped capability grants

agent_identities, tokens, grants, authority records, and channel subscriptions limit external agents.

≠

Candidate before authority

Collectors can propose without gaining permission to promote accepted organizational knowledge.

⏱

Current is not future

current_valid_assertions answers now; assertions_as_of() reconstructs another time.

◉

Every decision can be traced

Candidate edges, source refs, events, actor fields, and agent action logs explain how knowledge arrived.

⇄

Operational systems stay authoritative

link_record() and track_table() connect domain rows without making those systems point back to Rye.

Simple at every edge

Deploy, use, modify, and consume without adopting a framework.

Rye’s product advantage is not another agent application. It is a portable knowledge contract that agents and existing applications can share.

Autonomy is configured

Authority is data—not a prompt convention.

Capabilities answer “may this agent attempt the verb?” Domain authorities and claim policies should answer “may this interpretation become accepted knowledge without review?”

Provision a sales intake agent

Actual CLI commands from scripts/rye.

# Identity
./scripts/rye agents create \
  --key sales-intake \
  --label "Sales Intake Agent"

# Narrow verbs, one domain
./scripts/rye agents grant --key sales-intake \
  --capability rye.context.read \
  --domain account-updates

./scripts/rye agents grant --key sales-intake \
  --capability rye.candidate.create \
  --domain account-updates

# One-time-visible token
./scripts/rye agents issue-token --key sales-intake

Implementation review

The agent-driven vision exposes seven concrete gaps.

These are grounded in the current repository. The first two need security review; the central product gap is compiling policy into an automatic, explainable promotion decision.

P0

Authenticated read routes are not consistently capability- or domain-scoped.

When API auth is required, a bearer token is mandatory—but routes such as node search/detail, graph, events, disputes, dashboards, and workspaces call admin-scoped queries without a route-level domain capability check. Any valid agent token may be able to read beyond its grant.

P0

CDC events can preserve full sensitive domain rows.

capture_domain_change() puts complete old and new row JSON into event properties. Field redaction is implemented for node properties, not event payloads, so node visibility can expose fields that would otherwise be redacted.

P1

The secure MCP cannot yet answer ordinary entity questions.

rye.get_context_pack returns domains, authority, policies, and open candidates—but not accepted assertions, nodes, relationships, or recent events. The secure MCP does not expose the API's node knowledge endpoints, so “what changed on Acme?” is not yet an end-to-end secure-MCP workflow.

P1

Autonomy policy is recorded, but not compiled into the promotion decision.

Rye stores domain authorities, claim policies, source-of-truth policy, and agent autonomy policy. The promotion API currently checks the broad rye.authoritative.promote capability, then calls the lifecycle helper. It does not appear to evaluate claim type, authority basis, speech act, evidence, confidence, and risk as one explainable allow/review decision.

Neededauthorize_candidate_promotion()
allow · review · deny + reasons

P1

Reviewer capabilities exist, but reviewer MCP tools do not.

The API implements candidate status changes, generic promotion, source-policy acceptance, and CRM/PM plan acceptance. The secure MCP only registers review-queue reads; a reviewer agent must fall back to REST, the admin UI, or trusted SQL to finish the loop.
