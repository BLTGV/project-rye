- 2026-09-19: under FORCE RLS with a non-superuser owner, SECURITY DEFINER buys no visibility; policies still evaluate the caller's `app.*` variables. - 2026-09-19: a policy that reads its own table fails two ways. A direct subquery raises `infinite recursion detected in policy` for every session. Reaching the table through a function passes as admin and raises `stack depth limit exceeded` only when the policy fires for an agent. Policies on the governance tables follow the read order in the contract; tests must exercise the agent path on every table.
- 2026-09-19: `INSERT ... RETURNING` on an RLS table requires the SELECT policy to admit the new row. The error is the same `new row violates row-level security policy` text as a WITH CHECK failure. Generate the id before the INSERT when the writer may not read the row (`record_agent_action()`).
- 2026-09-19: `WITH cfg AS (SELECT set_config(...)) ... FROM tbl, cfg` and `FROM (SELECT set_config(...)) cfg CROSS JOIN LATERAL (...)` do not guarantee the role is set before the RLS filter runs; the planner can pull up the subquery and commute the join (`EXPLAIN ANALYZE` shows cfg `never executed`). They appear to work when an aggregate or LIMIT blocks pullup, and on any connection where an earlier `set_config(..., false)` already leaked the role. Set the role in its own earlier statement. In a psql script whose output is captured, use `SELECT set_config(...) \g /dev/null`; `-Atq` alone still prints the row.
- 2026-09-19: catching a helper's RAISE in a plpgsql EXCEPTION block rolls back the subtransaction, including the `record_agent_action` denial row written just before the RAISE. Tests that assert a denial was logged must not wrap the call that way.
- 2026-09-19: `SELECT ... FOR UPDATE` on an RLS table applies the UPDATE policy's USING clause as a silent filter, not an error. `assertion_update_policy` is role-independent, so even an admin session locks 0 rows on `assertions` unless the `app.write_path` gate is already open. `score_due_predictions()` (0019) locked before opening its gate and scored nothing on a non-superuser owner, leaving calibration reporting empty with no error; migration 0024 (work/006) opens the gate first. Rule: gate first, then lock, as `accept_assertion()` does. `FOR UPDATE` re-checks the qualifier after the lock is granted, so `CONTINUE WHEN <row>.id IS NULL` after a gated per-row lock is a real double-scoring guard.

- 2026-09-19: `assertions.subject_ref` is `GENERATED ALWAYS ... STORED`, so it is null inside every BEFORE trigger on `assertions`, for INSERT and UPDATE, and populated in AFTER triggers and in `OLD`. A BEFORE guard that compares `NEW.subject_ref` silently matches nothing; compute `coalesce('n:'||subject_node_id::text, 'e:'||subject_edge_id::text)`.
- 2026-09-19: `assertion_has_subject` is OR, not XOR, so a raw INSERT may set both subject columns; `subject_ref` then resolves to the node. `record_assertion()` and `governing_scope()` refuse that shape. Any guard that branches on "exactly one subject" and returns early has a hole.
- 2026-09-19: trigger functions that are SECURITY INVOKER read `assertions` under the caller's RLS, so `IF FOUND` means "visible and found". `assertion_read_policy` hides classified rows from `viewer`, `agent:*`, and an unset role, so a caller can make a check vacuous by classifying the row it just wrote above its own read level. A guard that validates such a row needs `IF NOT FOUND THEN RAISE`. The same hiding makes test fixtures with a classification pass vacuously: use `classification IS NULL` and confirm the row is visible before trusting a refusal.
- 2026-09-19: `assertion_update_policy` needs `app.write_path` plus the matching id in both USING and WITH CHECK. A probe that forgets to forge them gets zero rows and looks like a refusal.
- 2026-09-19: a suite that ends in ROLLBACK never fires a deferred trigger, and a plpgsql EXCEPTION block does not see one. `SET CONSTRAINTS <name> IMMEDIATE` works inside plpgsql; set it back to DEFERRED afterwards or `accept_assertion()` breaks later in the same transaction. For anything that must be durable, commit and re-read.

- 2026-09-19: `PERFORM set_config(...)` resets `FOUND`. After opening a gate and locking a row, test the row variable's id, not `FOUND`.
- 2026-09-19: a plpgsql `EXCEPTION` block makes each gate open and close a subtransaction, so a rollback restores the session variable by itself; an explicit clear after it is belt and braces.
- 2026-09-19: `IF x <> 'v'` on a NULL is not true, so it hides a missing value. Test 27 reported success for three unlabeled predictions until work/006 sharpened it. Compare with `IS DISTINCT FROM` in test assertions.

- 2026-09-19: `./scripts/test-nonsuperuser-owner.sh` (work/007, Operator-owned) runs the whole suite under a NOSUPERUSER NOBYPASSRLS owner in about 33 seconds and is a step in `./scripts/test-all.sh`. - 2026-09-20: under `scripts/test-nonsuperuser-owner.sh` there is no `rye_conformance` role; suites run as `rye_owner` with no SET ROLE, so the vacuity guard to assert is `rolsuper = false AND rolbypassrls = false`. - 2026-09-20: migration 0025 needed no change for the non-superuser owner, and test 31 fails without 0025 under both owner types.
- 2026-09-20: an RLS policy conjunct is not a rule about who may write, because on the superuser-owned Docker database every `SECURITY DEFINER` helper bypasses RLS entirely. work/009's first verification found `accept_assertion()`, `reject_candidate()` and `mark_assertion_outcome()` all working as `viewer` there and all refused on the non-superuser owner. Ruled in `docs/decisions/0009-who-may-write.md`; enumerate definer writers with `SELECT proname FROM pg_proc WHERE prosecdef`, never from a list in prose.
- 2026-09-20: `governing_scope()`'s witness branch runs *before* `DEFAULT_SCOPE`, so resolving with no witness does not merely lose the witness scope — it falls through to `DEFAULT_SCOPE`, which can be stricter. A helper that resolves with a witness and a guard that resolves without one can therefore disagree in either direction, and "the guard can only be looser" is false. Helpers take the stricter of both resolutions (`docs/decisions/0010-review-policy-holds-on-every-route.md`).
- 2026-09-20: `capture_domain_change()` runs in the application's own session on a tracked domain table, and the normal overlay deployment is an application that sets no Rye role at all. So anything that can refuse a graph write can fail the application's own INSERT, and anything that skips the event turns off the feature `track_table()` exists for. The CDC path does neither: it looks the node up under the caller's own visibility, then swaps `app.current_role` to the reserved role `system:cdc` around `record_event()` only and restores the caller's value on every exit path. `system:cdc` may only INSERT events and participants. `record_event()` generates the event id before inserting, so it never needs to read `events` back.
- 2026-09-20: a fresh worktree has no `node_modules`, so `./scripts/test-all.sh` dies at test 21 (`tsx: command not found`) or the site build (`astro: command not found`). Run `./scripts/bootstrap-worktree.sh` first, in the worktree only: it hard-links `admin/`, `site/`, and `skills/rye-source-context-intake/` `node_modules` from the main checkout when the lock hash matches (`--copy` for real copies, `--dry-run` to see the plan). It refuses to do anything in the main checkout, where dependencies are installed by hand; `npm ci` in `admin/` fails here because sharp builds from source. Hard links share inodes with the main checkout, so never run `npm rebuild` or patch-package in a bootstrapped worktree without `--copy`. Runbook: `docs/runbooks/deploy.md`.
- 2026-09-20: a policy-only role rule is only as strong as the database owner. Where the owner is a superuser (the default Docker install), every `SECURITY DEFINER` helper skips RLS, so a conjunct in a policy never runs inside it. A `BEFORE ROW` trigger is the only gate that binds a definer helper owned by a superuser; keep the policy conjunct as the second line. The definer writers to re-check after any policy-only change: `accept_assertion`, `reject_candidate`, `mark_assertion_outcome`, `resolve_knowledge_gap`, `promote_candidate_node_to_assertion`, `agent_create_candidate`, `agent_submit_observation`, `score_due_predictions`. Derive the list from `pg_proc WHERE prosecdef`, never by hand.
- 2026-09-20: refusal shape. A refused INSERT raises 42501. A refused UPDATE or DELETE by an ordinary session is zero rows on every owner type, because the policy filters the row before the trigger sees it; only a session that IS a superuser owner reaches the trigger and sees it raise. Assert the row and the row count, never the error text. An `UPDATE` applies the SELECT policies to the rows it scans, so a caller cannot end a row it cannot read.
- 2026-09-20: tables with no RLS are the last hiding place. Ask what a write steers (`node_source_map` decides which node CDC events attach to) and what a later write depends on (`crm_code_counters`: a rewound counter makes the next `create_task()` collide on `idx_nodes_external_unique`). `rye_may_write_table(text)` is the one place the "may this session write this table" answer lives, including that `system:cdc` may only insert events and participants; new supporting-table policies and triggers call it, not `rye_role_may_write()`.
- 2026-09-20: `role_classification_access` had an INSERT policy and no UPDATE policy until 0026, so on an RLS-bound owner no migration could change a seeded row. `migrate.sh` runs each migration in its own session, so a migration with DML sets `admin` itself. `CREATE POLICY` stores `false AND f()` unfolded, so a `pg_policies` grep is a sound `verify.sh` check.
- 2026-09-20: `capture_domain_change()` runs inside the application's own transaction, usually with no Rye role set. It records under the reserved `system:cdc` role, set around `record_event()` only and restored on the normal and exception paths, and writes `properties.session_role`. Never make it refuse: that fails the application's own write and breaks the overlay promise.
- 2026-09-20: helpers that insert an assertion resolve the governing scope twice, with their witness and with none, and take the stricter policy through `effective_review_policy()`, because the insert guard cannot see a witness (evidence is written after the assertion) and falls through to `DEFAULT_SCOPE`. Consequence: once `DEFAULT_SCOPE` is strict, an open source scope does not open a source, and rewriting `DEFAULT_SCOPE` is itself demoted, so it takes a suggestion and an acceptance. Set `DEFAULT_SCOPE` last on a test instance.
