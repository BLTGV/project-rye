- 2026-09-07: no down-migrations; rye_migrations tracks forward applies only. Rollback is restore-from-backup (docs/runbooks/deploy.md).

- 2026-09-08: record_event p_participant_roles is text[]; appending a bare literal (`arr || 'scope'`) raises "malformed array literal". Cast the element to ::text.
- 2026-09-08: record_scope_policy()'s own assertions land accepted even under a strict review policy, because governing_scope() returns NULL for a scope node's own policy assertions. Only helpers that pass p_scope_node_id feel the policy.
- 2026-09-08: enable_plugin_for_scope stores the manifest at properties.manifest; sync_plugin_metadata.sh stores properties.contributes. Read both, as rye_plugin_catalog() does.
- 2026-09-08: category vocabulary lives in migration 0020 (rye_categories, describe_category) with conformance test 28 and a `categories` CLI subcommand; contract in contracts/category-vocabulary.md.
- 2026-09-08: `./scripts/rye --scope <unknown key>` resolves to a NULL subquery and silently falls back to automatic scope selection; only an unknown uuid reports scope_found:false. Same for `context`.
- 2026-09-08: describe_category upserts the category node with ON CONFLICT DO UPDATE; an agent role without app.write_path=update_node_properties errors on a repeat describe. Conformance test 28 runs as admin only.
- 2026-09-19: the settlement lookup lives in migration 0021 (`rye_settlers()` plus `rye_settler_resolve_ref`, `rye_settler_is_agent`, `rye_settler_node_kind`) with conformance test 29 and a `settlers` CLI subcommand. It is read-only, STABLE, SECURITY INVOKER, and advisory: nothing in an acceptance path calls it yet.
- 2026-09-19: `rye_slugify_key()` maps every run of characters outside a-z0-9 to `_`. Both `ensure_knowledge_domain()` and `rye_settlers()` slugify the area key, and `create_agent_identity()` slugifies `agent_key`. A row written directly with a hyphenated key is invisible to the lookup, and a grant `authority_ref` of `agent:my-agent` never matches agent key `my_agent`. Use the helpers.
- 2026-09-19: `rye_settlers()` returns six `reason` values: `domain_not_found`, `domain_not_resolved`, `area_has_no_owner`, `area_owner_not_visible`, `area_owner_is_agent`, `no_settler_found`. `setup_gap` is true only for `area_has_no_owner` and `area_owner_is_agent`. An unknown explicit area key short-circuits to step `none` before the relationship step, so even the self default is suppressed. That fails closed.
- 2026-09-19: migration 0022 enables and forces RLS on the nine governance tables that 0016 created (work/004); the rules are in contracts/sql-surface.md, "Governance tables: who reads, who writes". `app.current_role` is the only agent binding (`rye_current_agent_key()`, `rye_current_agent_id()`); `app.current_user_id` is a label. The five write helpers stay SECURITY INVOKER and are admin-only because the table write policies are. `rye_settlers()` sees grants only for areas the caller may read, and the agent roster is readable to every session that can read an area, so the never-an-agent filter cannot fail open.
- 2026-09-19: the Docker test database owner `rye` is a superuser, so RLS is bypassed for it and for every SECURITY DEFINER function it owns. A green `docker-test.sh` run proves policies only where a test does `SET ROLE` to `rye_conformance`. To test the Supabase case, create a database owned by a `NOSUPERUSER NOBYPASSRLS` login role (extensions created first as superuser), run `install.sh` as that role unmodified, and point `DATABASE_URL` at it: `conformance.sh:36` skips `SET ROLE` for a non-superuser, so the whole suite runs in that configuration. Work/004's first verification failed on four bugs only this setup shows.
- 2026-09-19: under FORCE RLS with a non-superuser owner, SECURITY DEFINER buys no visibility; policies still evaluate the caller's `app.*` variables. The schema has two mechanisms and no others: rows the function needs are readable to the calling session, and writes on a caller's behalf are admitted by a transaction-local `app.write_path` gate set immediately around the statement.
- 2026-09-19: a policy that reads its own table fails two ways. A direct subquery raises `infinite recursion detected in policy` for every session. Reaching the table through a function passes as admin and raises `stack depth limit exceeded` only when the policy fires for an agent. Policies on the governance tables follow the read order in the contract; tests must exercise the agent path on every table.
- 2026-09-19: `INSERT ... RETURNING` on an RLS table requires the SELECT policy to admit the new row. The error is the same `new row violates row-level security policy` text as a WITH CHECK failure. Generate the id before the INSERT when the writer may not read the row (`record_agent_action()`).
- 2026-09-19: `WITH cfg AS (SELECT set_config(...)) ... FROM tbl, cfg` and `FROM (SELECT set_config(...)) cfg CROSS JOIN LATERAL (...)` do not guarantee the role is set before the RLS filter runs; the planner can pull up the subquery and commute the join (`EXPLAIN ANALYZE` shows cfg `never executed`). They appear to work when an aggregate or LIMIT blocks pullup, and on any connection where an earlier `set_config(..., false)` already leaked the role. Set the role in its own earlier statement. In a psql script whose output is captured, use `SELECT set_config(...) \g /dev/null`; `-Atq` alone still prints the row.
- 2026-09-19: catching a helper's RAISE in a plpgsql EXCEPTION block rolls back the subtransaction, including the `record_agent_action` denial row written just before the RAISE. Tests that assert a denial was logged must not wrap the call that way.
- 2026-09-19: `SELECT ... FOR UPDATE` on an RLS table applies the UPDATE policy's USING clause as a silent filter, not an error. `assertion_update_policy` is role-independent, so even an admin session locks 0 rows on `assertions` unless the `app.write_path` gate is already open. `score_due_predictions()` (0019) locked before opening its gate and scored nothing on a non-superuser owner, leaving calibration reporting empty with no error; migration 0024 (work/006) opens the gate first. Rule: gate first, then lock, as `accept_assertion()` does. `FOR UPDATE` re-checks the qualifier after the lock is granted, so `CONTINUE WHEN <row>.id IS NULL` after a gated per-row lock is a real double-scoring guard.
- 2026-09-19: `edges` columns are `source_id` and `target_id`.
- 2026-09-19: `conformance.sh` globs `tests/conformance/*.sql` and `migrate.sh` globs `schema/migrations/*.sql`; a new file needs no registration.
- 2026-09-19: when Docker is unavailable, the `pgserver` PyPI wheel (PostgreSQL 16.2) in a venv can execute a single migration and test against a prelude extracted from 0001, 0013, and 0016. It ships no `pgcrypto`, `btree_gin`, or `pg_trgm`, so `install.sh` cannot run on it and RLS interaction, migration ordering, and every other suite stay unverified. It is a stopgap, not the area test.
- 2026-09-19: the `rye` login in the Docker test database is a superuser, and superusers bypass RLS even when it is forced. `scripts/conformance.sh` detects this and runs under a non-superuser test role via SET ROLE, so the suite is sound. An ad hoc probe of role behavior must do the same, or every role will appear to see everything.
- 2026-09-19: `canonical_type()` reads `current_valid_assertions` under the caller's RLS. An alias that is classified, still a candidate, or outside `DEFAULT_SCOPE` does not resolve for that caller. Any rule keyed on a resolved type must therefore fail restrictive when the type is unrecognized, because "unrecognized" is what a blind caller sees.
- 2026-09-19: `link_record()` does not require the source table to exist. It reads `node_source_map`, falls back to `nodes.external_id` and `external_source`, inserts the node, and upserts the mapping. Only `track_table()` needs a real relation. So an external system works as a source: `source_schema 'github'`, `source_table 'issue'`, `source_id 'owner/repo#123'`.
- 2026-09-19: `link_record()` and `create_task()` collide. `create_task()` writes `external_id` as its `TSK-` code with `external_source 'internal'`, so a later `link_record()` for the same issue matches neither lookup and creates a second node. No helper attaches a source mapping to an existing node; only a raw insert into `node_source_map` does. A gap, documented in design/cookbooks/small-product-team.md.
- 2026-09-19: in `rye_settlers()` the `decision` speech act falls through to the area owner even when an `owns` edge exists. `statement_about_thing` is the speech act that returns the owner of a thing. A cookbook or skill showing an owner deciding about their own component must use `statement_about_thing` or a grant.
- 2026-09-19: `assertion_type_access.operation` has an inline CHECK, so a new operation value needs the constraint dropped and re-added. Its read and insert policies filter on `operation`, so a third value does not disturb them. `write` rows refuse through RLS and discard the statement; they cannot express "land as a suggestion instead".
- 2026-09-19: triggers on `assertions` fire in alphabetical order by name. `trg_assertion_settle_gate` sorts before `trg_assertions_immutable`, so the gate's message is the one a caller sees.
- 2026-09-19: `conformance.sh` runs each SQL file in its own psql session, so a file that never sets `app.current_role` runs with it unset. Every registry and scope-policy write in the repo already runs as admin.
- 2026-09-19: `assertion_update_policy` trusts `app.write_path` and the per-path `app.*_assertion_id`, which any caller can set. The 0019 immutability guard does still test `status`, but its allowance reads the same forgeable settings, so it stops nothing. A raw UPDATE can promote a candidate, end an accepted row with `superseded_by` still null, narrow a window, rewrite `attrs`, or change `classification`. Migration 0023 closes all of that for configuration types only. work/007 is the general case.
- 2026-09-19: there is no signal a Rye helper can produce that a caller cannot also produce. Session variables are forgeable, table privileges do not bind the owner (Supabase `postgres`, the Docker `rye` login), `PG_CONTEXT` can be matched by a caller-created function including one in `pg_temp`, and `current_query()` is text. So no rule may mean "a helper did this"; rules have to be about the row. Decision `docs/decisions/0008-the-row-is-the-gate-for-assertion-lifecycle.md`.
- 2026-09-19: exactly five functions issue an `UPDATE` against `assertions`: `mark_assertion_superseded` (0002), `propagate_assertion_classification_from_evidence` (0009), `record_assertion` (0023, window narrowing only), `mark_assertion_outcome` (0019), `accept_assertion` (0019). Everything else reaches those five. That is the chokepoint for anything about the assertion lifecycle.
- 2026-09-19: `supersede_assertion()` never consults the review policy — it inserts the replacement with the default status `accepted` — so any caller can write an accepted row under a `strict` scope by superseding and replacing. Separate from work/007 and untouched by it.
- 2026-09-19: `tests/conformance/30_configuration_gate.sql` asserts the message `%is Rye configuration%`, so `trg_assertion_settle_gate` firing before every other guard on `assertions` is load-bearing, not cosmetic. Both the C and `en_US.UTF-8` collations put it first against `trg_assertions_*`.
- 2026-09-19: `trg_assertion_evidence_required` (0009) is a `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED` on `assertions`, and `superseded_by`'s FK is deferrable too. Helpers point an incumbent at a replacement they have not inserted yet, and the partial unique index on accepted unsuperseded rows forces that order, so any rule about a replacement has to be checked at commit.
- 2026-09-19: `assertions.subject_ref` is `GENERATED ALWAYS ... STORED`, so it is null inside every BEFORE trigger on `assertions`, for INSERT and UPDATE, and populated in AFTER triggers and in `OLD`. A BEFORE guard that compares `NEW.subject_ref` silently matches nothing; compute `coalesce('n:'||subject_node_id::text, 'e:'||subject_edge_id::text)`.
- 2026-09-19: `assertion_has_subject` is OR, not XOR, so a raw INSERT may set both subject columns; `subject_ref` then resolves to the node. `record_assertion()` and `governing_scope()` refuse that shape. Any guard that branches on "exactly one subject" and returns early has a hole.
- 2026-09-19: trigger functions that are SECURITY INVOKER read `assertions` under the caller's RLS, so `IF FOUND` means "visible and found". `assertion_read_policy` hides classified rows from `viewer`, `agent:*`, and an unset role, so a caller can make a check vacuous by classifying the row it just wrote above its own read level. A guard that validates such a row needs `IF NOT FOUND THEN RAISE`. The same hiding makes test fixtures with a classification pass vacuously: use `classification IS NULL` and confirm the row is visible before trusting a refusal.
- 2026-09-19: `assertion_update_policy` needs `app.write_path` plus the matching id in both USING and WITH CHECK. A probe that forgets to forge them gets zero rows and looks like a refusal.
- 2026-09-19: a suite that ends in ROLLBACK never fires a deferred trigger, and a plpgsql EXCEPTION block does not see one. `SET CONSTRAINTS <name> IMMEDIATE` works inside plpgsql; set it back to DEFERRED afterwards or `accept_assertion()` breaks later in the same transaction. For anything that must be durable, commit and re-read.
- 2026-09-19: plpgsql `IF NOT (x = ANY(arr))` does not fire when `x` is null. `coalesce(x, '') <> ALL(arr)` is the null-safe spelling.
- 2026-09-19: `merge_nodes()` redirects the duplicate's `scope_governs_subject` edge onto the canonical node before the assertion copies are written, and `governing_scope()` breaks ties with `ORDER BY scope.id`. After a cross-scope merge both scopes govern the node and the lowest uuid wins, so a merge can move a node from a strict scope to an open one. Pin scope ids in any test that asserts a policy after a merge. Open as its own item.
- 2026-09-19: a `viewer` can archive an `onboarding_scope` node and its `scope_governs_subject` edge, and an `agent:t` can delete that edge. Either turns a strict scope into `open` for `record_assertion()` and for raw writes alike. `viewer` and an unset role can also insert assertions at all: `assertion_insert_policy` gates types, never roles. Open as its own item (what each role may write).
- 2026-09-19: `accept_assertion()` refuses an inferred candidate displacing a non-inferred accepted incumbent, and gates only `agent:*` callers on review policy; `viewer`, `team_member`, and an unset role may accept under `strict`.
- 2026-09-19: `mark_assertion_outcome()`'s `p_details` keys across all in-repo callers are exactly `outcome_reason`, `corrected_by`, `displaced_by`, `prediction_scored_event_id`, `outcome_assertion_id`, `brier_score`.
- 2026-09-19: once `verify.sh` requires an object, `install.sh` cannot build a tree without the migration that creates it. Use `scripts/migrate.sh` directly for a negative-control install.
- 2026-09-19: Docker test runs need their own `COMPOSE_PROJECT_NAME` as well as `RYE_POSTGRES_PORT`: `--reset` under a shared project name drops another session's volume, and a released port is taken by another session within minutes. In a fresh worktree `npm ci` in `admin/` fails (sharp builds from source); copy `admin/node_modules` from the main checkout or the flow dies at test 21 with `tsx: command not found`.
- 2026-09-19: `SET app.current_role = ...` is a syntax error because `current_role` is reserved. With ON_ERROR_STOP off the probe carries on with no role set, and an unset role can still write assertions, so the probe appears to work. Use `set_config()` and read the value back.
- 2026-09-20: `accept_assertion()` is SECURITY DEFINER while `record_assertion()` and `supersede_assertion()` are not, and the Docker owner `rye` is a superuser that FORCE ROW LEVEL SECURITY does not bind. So in the test database `accept_assertion()` reads and ends rows the caller cannot see; on Supabase, where the owner is not a superuser, it does not. "The guard reads what the helper reads" must name the helper and the deployment.
- 2026-09-20: a caller cannot hide a row after writing it: `classification` is immutable without derivation evidence and the subject columns are immutable. A commit-time visibility check can only be beaten by a row written invisible from the start.
- 2026-09-20: `RETURN NULL` in a constraint trigger's first branch skips every later check in the function. Fall through with `IF ... ELSIF`.
- 2026-09-20: `assertion_evidence`'s insert policy needs a visible `event_id` or `source_assertion_id`; a `witness_node_id` alone is refused for every role. A bare `(assertion_id, kind)` insert is refused too, admin included. Use `append_assertion_evidence()`.

- 2026-09-19: `PERFORM set_config(...)` resets `FOUND`. After opening a gate and locking a row, test the row variable's id, not `FOUND`.
- 2026-09-19: a plpgsql `EXCEPTION` block makes each gate open and close a subtransaction, so a rollback restores the session variable by itself; an explicit clear after it is belt and braces.
- 2026-09-19: `IF x <> 'v'` on a NULL is not true, so it hides a missing value. Test 27 reported success for three unlabeled predictions until work/006 sharpened it. Compare with `IS DISTINCT FROM` in test assertions.
- 2026-09-19: any test comparing `rye_settlers()` answers across roles takes one baseline per role. `viewer` and `team_member` are in `role_classification_access` and see every area; the unset role and an agent-shaped role naming no identity see none and get `domain_not_found`; a bound agent holding a grant on the area gets the full answer. Test 30 (work/005) assumed one admin baseline and broke when it met migration 0022.
- 2026-09-19: open. `merge_nodes` (0005, about lines 164-169) takes `FOR UPDATE` on `nodes` with no gate open. Under an `agent:` role on a non-superuser owner the lock is filtered by `node_update_policy` (0007) and it raises the misleading `Duplicate node <uuid> not found`. Hidden in Docker. No row locks exist in 0020-0023 or the profile migrations, and there is no `UPDATE ... RETURNING` anywhere.
- 2026-09-19: run `conformance.sh` from the host, not inside the container, when you want `21`, `22`, and `23` to execute; inside the postgres container they self-skip because node is absent.
- 2026-09-19: when a self-settled type's registry entry is missing, `rye_settlers()` does not return `none`; sighted roles fall through to step `area_owner`. A test that checks a settlement baseline names the expected settler; a non-empty answer proves nothing.
- 2026-09-19: `./scripts/test-nonsuperuser-owner.sh` (work/007, Operator-owned) runs the whole suite under a NOSUPERUSER NOBYPASSRLS owner in about 33 seconds and is a step in `./scripts/test-all.sh`. Run it before calling any RLS, SECURITY DEFINER, or row-locking change done. It shares the compose project with `docker-test.sh` in the same checkout, so do not run the two at once.
- 2026-09-19: in a psql script, `:'var'` interpolation does not reach inside a dollar-quoted block; interpolate before entering `$$`. `boolean || text` renders `true`/`false`, not `t`/`f`.
